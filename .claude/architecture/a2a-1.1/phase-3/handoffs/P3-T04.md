## Interfaces and behavior

- `TaskProposal` carries a nonblank correlation ID, nullable immutable
  `TaskSnapshot` base and proposed Task. The submission service accepts a null
  base only with a retained opening `RequestContext` containing the opening
  message and matching task ID. It never reads a newer revision to stamp an
  already-built proposal.
- `AgentEmitter.submitTask(TaskProposal)` returns `CompletionStage<ProposalResult>`;
  `refreshTask()` returns the authoritative Task/revision pair. `refreshTask`
  does not create a Task or alter any captured proposal base. The emitter also
  exposes `addProposalResultListener`, `lastProposalResult` and bounded local
  `proposalCompletion(correlationId)` lookup for void-path results and late
  completions.
- Results are correlated `Committed`, `Rejected` (conflict/validation plus
  permitted current revision), or `Failed` (known non-commit/indeterminate).
  The underlying completion is claimed once. Results and sink callbacks are
  completed on the common callback pool, outside authority/event processing.
  Queue admission is not commit acknowledgement; commit completion says nothing
  about subscriber or webhook delivery.
- Admission uses a 5-second default timeout; result observation uses a
  30-second default. `DefaultRequestHandler.Builder` has millisecond setters,
  and CDI config uses `a2a.task-proposal.admission-timeout.millis` and
  `a2a.task-proposal.result-observation-timeout.millis` from
  `META-INF/a2a-defaults.properties`.
- On observation timeout the returned stage receives a correlated
  indeterminate `Failed` observation. The underlying future remains available
  through `proposalCompletion(correlationId)` and can later complete with the
  actual result; no mutation is cancelled or retried. Each execution-local
  service retains at most 1024 submissions. Completed results expire after
  five minutes and may be evicted earlier under capacity pressure; in-flight
  submissions are not evicted. If all entries are in flight, the new result is
  asynchronously reported as known non-commit without an index entry.
- `addTask` and `emitEvent(Task)` adapt to proposals using the immutable
  invocation-start snapshot. A later acknowledged result does not advance that
  base. Executors may rebuild from explicit `refreshTask()` and submit a new
  proposal. The default handler builds the execution context/sink before both
  execute and cancel invocation. Void outcomes update `lastProposalResult` and
  reach registered listeners asynchronously.
- Raw local full-Task queue admission without a proposal envelope is rejected
  synchronously before queue acquisition. The old two-argument `AgentEmitter`
  constructor remains, but its full-Task methods now fail explicitly without
  execution provenance. Other event methods retain their existing path.
- Proposals use a new internal queue item. The processor handles it outside the
  shared A2A event path, releases the queue permit and does not broadcast,
  mutate task failure state, push, replicate or establish final-event
  expectations. T03 committed snapshot/finality/result-Task metadata and
  producer isolation are retained. No arbitrary Task is promoted into a
  committed envelope.
- Production authority is intentionally bounded pending T05: a matching-base
  unchanged Task returns a validated unchanged `Committed`; a stale base returns
  `Rejected(CONFLICT)` with the current revision; a changed full Task or first
  materialization is validation-rejected until normalization exists. Legacy-only
  stores fail explicitly because they cannot provide atomic provenance. The
  injected authority tests exercise successful commit and rejection plumbing;
  this task does not enable replacement writes.

### Corrected interfaces and behavior

- `TaskProposal` now retains a correlation ID, a deeply copied immutable
  nullable `TaskSnapshot` base, and a defensive copy of the proposed Task.
  Snapshot copying covers nested JSON map/list metadata and message/artifact
  values. No fresh revision is read to stamp an already-built proposal.
- `AgentEmitter.submitTask(TaskProposal)` returns a protected
  `CompletionStage<ProposalResult>`, and `refreshTask()` returns a matching
  authoritative Task/revision pair without changing older proposal bases.
  `addTask` and `emitEvent(Task)` retain the invocation-start snapshot, including
  after their own acknowledged proposals; refresh plus explicit rebuild is the
  only way to use a newer base.
- A registered submission owns a private-constructor
  `ExecutorSubmissionService.ProposalAdmission` capability carrying that exact
  submission. It is claimed once, and processing checks owner and map-entry
  identity. Public arbitrary `processAdmitted(TaskProposal)` and public raw
  proposal enqueue are absent. A matching correlation ID cannot substitute a
  different proposal.
- Main-queue local full-Task admission rejects synchronously before queueing
  unless it carries the internal proposal capability. Forged proposal,
  committed-snapshot, result-Task, or finality metadata is not sufficient.
  Existing public event descriptors remain, and trusted replicated ingress
  retains its separate marker path. `EventQueue.isForTask` defaults to false;
  custom queues must affirm their task binding before proposal admission.
- Queue admission reports only admission. The processor's local proposal path
  consumes/releases the item without shared broadcast, task mutation, push,
  replication, or final-event expectation. Only authority processing produces
  `Committed`, `Rejected`, or `Failed`; rejection completes its origin's result
  path and does not become an A2AError, task failure, subscriber failure,
  webhook, or replicated event.
- Typed admission timeout/interruption is known non-commit. An arbitrary
  runtime exception from a virtual queue call is indeterminate because that
  queue may have forwarded the item before throwing; its correlation remains
  retained for late in-process authority completion. Completion, observed
  stages, and sinks are protected from caller mutation. Result callbacks and
  sink callbacks are dispatched away from authority processing and the event
  processor. The observed stage and the underlying result stage are dispatched
  separately, so a dependent callback that waits on the other channel cannot
  block its completion. Admission-dispatch failure callbacks are also
  dispatched rather than run inline on the queue caller.
- Default deadlines remain 5 seconds for admission and 30 seconds for result
  observation. Builder and CDI values must be positive; tests inject shorter
  values. Observation timeout yields an indeterminate observation but neither
  cancels work nor drops the correlation. The eventual authority outcome remains
  locally available and timeout does not authorize retry.
- Result lookup has a capacity of 1024 registered submissions per execution
  service. Pending submissions are never evicted. Capacity pressure rejects a
  new registration with known non-commit. Entries with authority evidence are
  retained for five minutes from that evidence, then pruned on later lookup or
  submission. An uncertain forwarded proposal stays pending until authority
  evidence arrives, subject to the fixed capacity. This is an in-process bounded
  lookup only; no durable result index, wire receipt, or public status RPC was
  added.
- The default request handler installs the execution-local result sink before
  execute and applicable cancel invocations. Retained void emitter outcomes
  update execution-local `lastProposalResult` and notify listeners
  asynchronously. Cancellation captures Task and atomic snapshot as one pair
  before queue allocation, and closes the created child on all invocation/error
  paths.
- Production authority supports current-value unchanged results, full-snapshot
  conflict rejection, and validation rejection. Changed full-Task normalization
  and first materialization remain guarded for T05; raw full Tasks are not
  promoted into committed replication envelopes. Legacy-only stores fail
  explicitly because they lack atomic snapshot capability.

### RR1–RR5 corrections

- **Typed admission failures:** `EventQueue.QueueAdmissionToken` has a private
  constructor and binds a proof to the owning `MainQueue` and exact item.
  MainQueue records acceptance only after submission to the bus, and records
  rejection only when semaphore timeout/interruption occurs before submission.
  `ProposalAdmission` finalizes a known rejection atomically; a late item cannot
  subsequently process. An adapter exception without that proof, including a
  typed timeout/interruption after forwarding, returns an indeterminate
  observation and retains the underlying completion for eventual authority
  evidence. Tests cover both typed exceptions after forwarding, the real full
  queue pre-admission timeout, and an unproven typed timeout.
- **Final results versus observation notices:** the local sink now receives an
  internal final/not-final distinction and a supplier for the current final
  authority result. It delivers authority failures even when their cause is a
  `TimeoutException`; it suppresses an observation or dispatch notice if a
  final result arrived while that notice waited. `ExecutionProposalContext`
  checks current final state before updating `lastProposalResult` and before
  each listener, restoring the final result if it races with a notice. This
  prevents an earlier slow listener from causing later listeners to receive an
  obsolete timeout after commit. Tests exercise an authority timeout failure,
  forwarded timeout/interruption notices followed by commits, and two listeners
  interleaved around a blocked timeout listener.
- **Deadline scheduler:** a timeout worker now wins the observation decision
  with an atomic compare-and-set and dispatches stage completion and sinks to
  the callback executor. It never runs client continuations on scheduler
  threads. The existing cached callback dispatcher can start additional workers
  while unrelated client continuations wait. A bounded four-blocked-continuation
  test confirms a fifth submission still observes its 250 ms deadline.
- **Status-message immutability:** `ImmutableTaskCopy` now deep-copies the
  top-level Task status message and `TimelineEntry.StatusValue` status message
  through the same Message payload/metadata copying path as history and
  artifacts. Separate source-list mutation assertions cover the snapshot's
  top-level status and the proposal's timeline status.
- **Negative and zero monotonic origins:** result expiry uses elapsed subtraction
  from the completion reading and the existing final-result marker; it does not
  interpret positive time as a completion sentinel. A controlled clock test
  proves expiry and correlation reuse from both −1000 ns and 0 ns origins.
