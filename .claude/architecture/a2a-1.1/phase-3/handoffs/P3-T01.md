## Frozen API and behavior

The six contract types retain the approved fields and core signatures:

```java
record TaskRevision(long value) {}
record TaskSnapshot(Task task, TaskRevision revision) {}
record MutationPlan(Task task, List<StreamingEventKind> events, boolean changed) {}
record CommittedMutation(TaskSnapshot snapshot, List<StreamingEventKind> events, boolean changed) {}
interface TaskMutation {
    MutationPlan plan(@Nullable TaskSnapshot current);
}
interface AtomicTaskStore extends TaskStore {
    @Nullable TaskSnapshot readSnapshot(String taskId);
    CommittedMutation mutate(String taskId, TaskMutation mutation);
}
```

`AtomicTaskStore` also has a callback overload for T03:
`mutate(String, TaskMutation, TaskCommitSlotCallback)`. The callback reserves a
local slot inside the per-task `ConcurrentHashMap.compute` boundary. It is limited
to bounded local reservation work: no fan-out, network, executor, or user work.
The supplied token starts reserved; it is marked publishable only after the map
replacement returns definitively. A runtime reservation failure leaves state
unchanged, cancels the token, and throws `TaskMutationNotCommittedException`.
Unexpected runtime failure from the storage compute path cancels the token and is
reported as `TaskMutationOutcomeUnknownException`; it is not presented as a
rollback. Errors cancel any reserved token before propagating. Cancellation and
publishability are observable through the token's state methods.

The in-memory store reads an immutable `(Task, TaskRevision)` pair from one stored
entry. `TaskMutation.plan` runs once inside the keyed compute; it is not retried.
An unchanged plan returns the current snapshot and no events without consuming a
revision or reserving a slot. A changed plan stores the supplied final task and
returns one final snapshot with the original ordered event objects. A batch with
event generations 2 and 3 therefore returns those events plus only its final
generation-3 snapshot.

Storage revisions use a store-local monotonic sequence, independent of protocol
generation. The sequence advances inside the keyed compute for successful changed
mutations and legacy `save` calls. This avoids revision reuse after delete/recreate
without retaining per-ID tombstones. Failed attempts can leave gaps; revisions
are opaque comparison tokens, not a protocol counter. `delete` removes the stored
entry atomically and keeps the store-local sequence for later creations.

`TaskStore` methods and descriptors, existing `InMemoryTaskStore` constructors,
authorization/list behavior, and `TaskStateProvider` decisions remain intact.
Legacy `save` now atomically replaces the stored task/revision entry while
preserving the task's protocol generation; legacy `get` unwraps that entry;
legacy `delete` removes it under the same keyed map operation. A compile-only
nested legacy store in the contract test implements `TaskStore` without adopting
`AtomicTaskStore`. Existing runtime handlers and bus callers are not wired through
`TaskMutationAuthority` in T01.

The revision-sequence choice and two-phase local slot token are implementation
decisions for this handoff. The slot token lets T03 retain an ordered placeholder
before replacement while preventing publication until definitive commit; its
in-memory state does not provide crash recovery or a durable outbox.

`TaskCommitSlot` is now a read-only view. External `AtomicTaskStore`
implementations create a public `TaskCommitSlot.Reservation` handle through
`TaskCommitSlot.reserve`, retain that handle privately through storage replacement,
and pass only `reservation.slot()` to the callback. The callback can inspect and
retain the view but has no transition method. The store marks its retained
reservation publishable only after definitive replacement, or cancels it on a
failure. The external-package fixture compiles and exercises reservation, commit,
cancellation, and terminal-state behavior through this API. `isCancelled()` means
only that local publication is suppressed; it does not assert whether storage
committed.

The added regression first reproduced the defect: before the API change, reflection
invoked the callback-visible public `markCommitted()`, then the callback threw.
The store left the task unchanged and the retained slot publishable. After the
change, that attempt cannot access a public transition method; the callback throws,
its slot is cancelled, and the task remains unchanged.
