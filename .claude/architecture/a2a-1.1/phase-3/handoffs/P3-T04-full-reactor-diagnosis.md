`DefaultRequestHandler.initMessageSend` calls `TaskManager.updateWithMessage` for an existing task and obtains the post-input store snapshot for the invocation. `AgentEmitter.emitEvent(Task)` calls `addTask`; `ExecutionProposalContext` supplies the immutable invocation base. The production `ExecutorSubmissionService.forTaskStore` compares that base with the current pair. A verbatim echo gets `Committed(changed=false, events=[])`; the WORKING proposals and the push fixtures with omitted history fail the subsequent whole-Task equality check and get the deferred-normalization rejection. That is separate from a stale-base conflict. The bus proposal branch calls `ProposalAdmission.process()` and returns after releasing the permit. It never reaches the committed delivery path. The later independent artifact and terminal delta still proceed. The original 0.3 push failure explicitly reports two stream responses and two notifications.

**Move one existing-task slice of T05 into the regression repair.** An output-only adapter can deliver a verified echo. It cannot produce the WORKING response with a matching committed state, revision and generation while the authority rejects the underlying change. The required slice is matching-base normalization of **existing-task equivalent and status-only proposals**, plus version-selected projection of their authoritative results. Initial Task materialization is guarded in the checkpoint, but none of these eight failures requires it. The rest of T05 stays held, including initial materialization and opening-input deduplication, full artifact and metadata normalization, multi-mutation ordering from a single proposal, and migration examples. T06–T11 work stays in its assigned scope.

The [architecture's full-Task rules](../../architecture.md#full-task-output-from-executors) and [older-client views](../../architecture.md#older-client-views-of-shared-tasks) govern the repair, together with [A04/A05/A06/A07 and A11](../../acceptance.md) and the [approved T03/T04/T05 boundaries](../implementation-plan.md#p3-t05--normalize-full-task-proposals-safely). T05's acceptance sentence “No-op emits nothing” needs an explicit, narrow interpretation for this correction. A verified no-op emits zero **canonical mutations**. The older initiating response and older webhook contract still require a Task snapshot **delivery**. Applying that sentence to every delivery would directly conflict with six of the eight tests. Record this distinction in the correction disposition. The reply/notification summarizes existing state at its existing revision and watermark. It has no generation position of its own and carries no new wire fields.

## Minimal correction design

1. **Check and plan under the store's atomic boundary.** In the production path of `tasks/ExecutorSubmissionService.java`, use `TaskMutationAuthority.mutate` with the same slot reservation mechanism as T03. Validate the task/context and immutable base pair against the authoritative snapshot inside the planner, including for the unchanged case. A changed revision conflicts even if the proposed agent-owned values happen to match. Keep the original execution base, registered admission and result sink. Discard any slot on definite non-commit or unknown outcome and retain T04's certainty/correlation semantics. Keep the missing-base, missing-task and legacy-only store guards. Preserve the typed local rejection and observed-current revision from the same atomic check. This needs no change to `TaskStore` or `AtomicTaskStore`.
2. **Limit normalization to the two required outcomes.** In `tasks/TaskMutationPlanner.java`, compare supported agent-owned values and use the canonical task as the starting point. Ignore supplied Task generation, history and timeline as mutation inputs. Omitted artifacts and metadata retain their stored values, including USER artifacts. An equivalent artifact carried in a full snapshot contributes no edit; compare content and origin without trusting supplied sequence ranges, and keep cross-origin collisions and any actual artifact or metadata changes outside this slice as typed validation rejections. For unchanged status, return the exact authoritative pair with `changed=false`, no events, no revision/sequence allocation and no reservation. For a changed status, use the existing canonical status planner and its terminality checks. Retain history, timeline and artifacts and append only the legitimate status mutation, with its normal status-message handling. Keep the T07 migration of existing input admission outside this correction; the proposal consumes the already-accepted history and immutable pair.
3. **Publish changed results through T03.** In `events/MainEventBusProcessor.java`, supply the reserved production commit's batch to the existing `OrderedTaskPublisher` and reuse committed batch admission, push ordering, fan-out and post-commit failure handling. Carry optional legacy Task summary information as internal delivery metadata referencing that batch's matching snapshot. `events/LocalEventQueueItem.java` and the item-to-event mappings in `requesthandlers/DefaultRequestHandler.java` (ordinary send and subscribe) are the existing seams. Select the Task in 0.3/1.0 and the canonical stamped status in 1.1. Preserve the queue item's canonical finality and the unary `tasks/ResultAggregator.java` matching-snapshot logic. The existing transport projections and compat conversion can then strip generations/timeline/USER artifacts and apply the established history rules. Keep replication, lifecycle and committed push admission on the canonical event. Deliver exactly one view per subscriber and config.
4. **Deliver verified no-op snapshots at the proposal's processing position.** From the production admission's confirmed unchanged result on an active task, give the initiating legacy consumer one internal Task snapshot. Keep this delivery scoped to the active-task cases in the failing tests. A no-op on an already-terminal task must not synthesize finality or re-notify. Use the exact authority result after processing, before processing the next bus item; no delayed callback or fresh store read. The current bus serializes local events, joins changed ordered publication before taking the next item, and owns the local push chain. Insert the no-op legacy push into that same per-task chain, respecting earlier committed-batch admission and later deltas. In `tasks/BasePushNotificationSender.java`, select the view using each **stored config's delivery version**, reusing its existing projection/formatting. A 1.1 config gets the canonical status for a changed result and skips the no-op. A 1.0 config gets the Task summary; a 0.3 config uses the matching Task snapshot formatter. The 0.3 no-op precedes the artifact snapshot, including when push admission or sending is deferred. Keep no-op delivery out of committed mutation batches, canonical callbacks, replication, unrelated streams and terminal lifecycle. Its admission has zero mutation positions, so it must not masquerade as a committed position or skip ahead of a deferred committed push. Preserve the public sender SPI. A sender without version selection must never receive an unconditional legacy-only snapshot. T11 will need to carry this distinction into its shared dispatch gate if it later routes this local compatibility path.
5. **Keep mutation provenance inside trusted production wiring.** The injected `ProposalAuthority` used by T04 tests and the externally observable `ProposalResult` are insufficient publication proofs. Pass internal reservation/batch evidence through the admitted production path in `ExecutorSubmissionService` and the processor. A delivery failure after confirmed commit must preserve the exact local committed outcome. Keep queue permit release in the outer path and dispatch local result listeners off processor/authority locks. Raw Task enqueue and caller-manufactured queue metadata retain their T04 rejection.

The implementation should reuse `VersionedOutputProjector` for field projection and only touch it if that avoids duplicating the version selector. Binding codecs, transport handler signatures and wire contracts need no changes. The correction needs neither a custom TaskStore adapter nor a return to raw Task persistence.
