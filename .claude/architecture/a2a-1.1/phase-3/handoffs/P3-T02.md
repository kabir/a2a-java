## Interfaces and behavior

Added server-local, immutable request admission data and a pure planner:

```java
record PendingTaskInput(Message message,
        List<TaskArtifactUpdateEvent> artifactUpdates,
        MessageSendConfiguration configuration,
        Map<String, Object> metadata,
        Admission admission,
        OffsetDateTime receivedAt) {}

record Admission(String taskId, String contextId, String tenant,
        boolean authorized, boolean userArtifactsEnabled) {}

enum MutationOrigin { USER, AGENT }

MutationPlan planInput(@Nullable TaskSnapshot current,
        PendingTaskInput input, MutationOrigin origin);
MutationPlan planStatus(TaskSnapshot current, TaskStatusUpdateEvent status);
```

The five-argument `PendingTaskInput` constructor captures request time before an
atomic callback. The planner itself reads no clock and calls no authorization,
agent-card, store, or user code. Admission carries the resolved tenant, task and
context identity, authorization result, and effective-card `userArtifacts`
capability. Existing-task identity and terminal state are checked from the
authoritative snapshot inside the planner callback.

`planInput` compares `ifGenerationMatch` once with the authoritative pre-batch
task generation. It validates the entire input before returning one `MutationPlan`
with ordered canonical events and a single final Task. Generation stamps from
input messages/artifact events/status events are ignored. Opening M is generation
1, opening artifacts follow in list order, a separately supplied status advances
once, and the final Task summarizes the last event generation. Baseline SUBMITTED
status uses the pre-callback request timestamp and consumes no event generation.

Messages and statuses update timeline independently from legacy history. Replacing
a status preserves the existing TaskManager behavior of moving the previous
status message into history; receiving a message likewise moves the prior status
message to history, clears it from status, and appends the input message. Artifact
updates do not create timeline entries. Replacement resets artifact start/end
ranges to the assigned generation; append retains a known start (or starts at the
new generation for a legacy zero-range artifact), advances end, merges parts and
metadata, and preserves `lastChunk`.

Artifact identity is the current task plus artifact ID. Missing legacy origin is
treated as AGENT. Omitted new origin is normalized from `MutationOrigin`; explicit
inconsistent roles and edits in either cross-origin direction raise
`InvalidParamsError`. USER artifacts remain canonical and are preserved during
unrelated agent updates. USER artifact input requires the resolved effective-card
capability. Artifact-only input is accepted for an existing task and rejected for
creation. Authorization denial preserves `TaskNotFoundError`.

At initial implementation, `TaskMutationAuthority` rethrew these typed errors
from the store wrapper; the correction below narrows that behavior to errors
originating from the planner callback. It does not unwrap uncertain outcomes.

## Limits and next action

- This is a pure planner and admission model only. No ordinary send, direct
  Message branch, handler, bus publication, executor, TaskManager, JPA, replication,
  migration, replay, client reduction, or live operation is wired or implemented.
- The selected G4 bootstrap trace and G6 artifact-origin policy remain experimental
  SDK policies; their normative clarification gates are still open.
- Appending to a nonexistent artifact is rejected as invalid parameters. This
  implementation does not add receipts, idempotency, automatic retry/rebase, or
  new protocol errors.
- `TASK_STATE_UNSPECIFIED` is treated as terminal for fresh planner mutations in
  line with its TaskState documentation, although the shared enum's `isFinal()`
  flag is false for that value. The shared model was left unchanged.
- No full reactor build, public binding integration test, external authorization
  provider, JPA, or multi-instance behavior was tested in this assignment.
