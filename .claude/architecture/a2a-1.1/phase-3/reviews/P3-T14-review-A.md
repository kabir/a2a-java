Real-timing derivation (read latency l in [0,deadline), ticks 5s apart): sighting <= loss+10s; closing read needs 5j+l_j-l_k>=10, i.e. j=2 or j=3, so closure < sighting+20s => < loss+30s. The Javadoc figure of 30s (:64-71) is a correct, conservative upper bound (my tighter figure is ~25s+scheduler delay); no instantaneous-repair, retryability or new-error-code claim (:59-62 explicitly disclaims them; error text only says "retry ... or call GetTask").

A task deleted/expired while observed is never judged stranded or closed by the reconciler; observer then depends on the queue closing. Scenario: store evicts task, stream stays open indefinitely. Not in the stated bound scope for lost publication; document or treat as failure.
F-A1-2 Info, :343/:636: reorder-gap and read-deadline are only evaluated at ticks, so a gap closes at 10s..15s, and a hung read at 5s..; Javadoc phrase "next tick after its deadline" is accurate. Under load a slow (>10s) but healthy publication causes a false close - inherent SDK policy (:83).

## A2. Authority-read bounds
Verdict: Mechanism accepted; one Medium finding on the production reader pool.
Verified: one read per TaskWatch per tick (:341-366); an in-flight read is not duplicated (:342-345); abandoned+cancelled at its deadline then `failAll` (:346-353); late completion ignored by `watch.inFlight != read` identity test (:373); failure/null head -> `failAll` (:379-382). A stale `onRead` cannot touch a newer observation: when the last observer leaves, the watch is removed from `watches` and a new attach builds a *new* TaskWatch (:246), and `abandonRead` nulls `inFlight` (:261), so the old completion returns at :373; within one watch a stale-low head only resets suspicion (:642), never raises it.
F-A2-1 Medium, :438-439/:457-459 (+ :356-361,:379-382): `StoreAuthorityHead` pool is `ThreadPoolExecutor(0,4,..,SynchronousQueue)` with the default AbortPolicy. `tick()` submits one read per watched task back-to-back; the 5th concurrent submission while 4 reads are still running is rejected -> `completeExceptionally` -> `AUTHORITY_READ_FAILED` -> `failAll` closes every healthy observer of that task. Scenario: >=5 tasks with subscribers on a DB-backed store (read of a few ms) -> at the first tick the 5th..Nth tasks' streams are killed with InternalError although nothing was lost. No test exercises >4 tasks (grep: no Rejected/saturation test). Fix: bounded queue / defer to next tick instead of failing on rejection.
F-A2-2 Low, :350-353/:465: `expired.cancel(true)` on a CompletableFuture does not interrupt the reader thread; a hung store call keeps one of the 4 reader threads indefinitely (bounded by 4, then F-A2-1 rejection path applies). The reconcile-vs-unregister race (:337 then :363-365) can also install a read on an already-removed orphan watch: its completion is harmless (empty observer set) but is never cancelled.
F-A2-3 Info, :393-397: any read failure/deadline closes all observers of that task, including ones attached after the read began (matches "affected" = same task; test :90 only covers up-to-date observer in a stranded case).
Discriminating check: probes `readdeadline` (fails :226) and `readfailure` (fails :195) each have a sole failing test; no other test asserts these reasons. Read-never-completes cannot persist: it is cleared at the first tick >= deadline while the watch has observers; with no observers the read is cancelled at :268.

## A3. Buffer limits
Verdict: Accepted with Low findings; no path found that lets *held* or *queued* committed items exceed 256/4 MiB.
Walked: every charge goes through `tryChargeLocked` under `lock` (:542, :587) and is released exactly once: on duplicate (:546,:592), on covered discard (:600), on consumption (:562-564, `noteConsumed` at EventQueue:1284/1294 only for items present in the identity map), and wholesale in `fail` (:665-668). Pre-install items in `complete()` are charged before the held map is trimmed (:584-594) and a duplicate is uncharged; overflow there breaks out before `attached` is set and calls `fail` (:606). Terminate purge (EventQueue:1354-1355) is paired with the counter reset, so no double release.
F-A3-1 Low, :542-546: charge happens *before* the duplicate check, so a duplicate held generation arriving when the buffer is exactly full (e.g. a remote redelivery of a held generation with 256 held) raises a false BUFFER_OVERFLOW although nothing would grow. Fix: test `held.containsKey` first.
F-A3-2 Low, :534/:399-405: `sizer` (full JSON serialisation) runs per observer per event on the distributor thread, even for stale/duplicate items (computed before :538) - cost scales with observers x event size; and one event larger than 4 MiB can never be admitted, so every such event closes every observer with BUFFER_OVERFLOW regardless of consumption rate.
F-A3-3 Info, EventQueue:1284/1294 + EventConsumer:95-100: the charge is released at `dequeueEventItem`, but EventConsumer then pushes into a 256-slot Tube buffer; "delivered-but-unconsumed" therefore measures the child queue only, so a non-demanding HTTP client is covered only after the downstream tube buffer fills (not examined further). Non-committed items (generation 0, :530-533) are not charged (queue capacity bound only).
F-A3-4 Low, EventQueue:1226 vs :1323: `observation` is volatile, but an item that read `null` before `installObservation` and calls `offerToQueue` after `complete()` ran `takeQueuedCommittedItems` would bypass the gate (possible duplicate of a covered generation). Window is a few instructions vs an I/O snapshot read; theoretical.
Discriminating check: probe `overflow` fails exactly the 3 limit tests (:250,:271,:291) and `preinstall` fails :471; `slowDemandIsNotAGap...` (:299-317) runs 12 ticks with head 10 and consumer idle, watermark==10 so `head<=watermark` (:642) - no false gap. The 256/4MiB tests assert the exact-limit-passes boundary (:246,:266), so an off-by-one would fail.

## A4. Cleanup
Verdict: Accepted; Low/Info findings only. Every exit funnels into `unregister` (:251-270): terminal delivery (:554-556, :608-610), child close (EventQueue:1406-1409 -> :619-623), `fail` (:670), and handler rejection via `detach()` -> `child.close(true)` (DefaultRequestHandler:1536-1542). `unregister` removes the watch with its last observer, cancels its read (:261,:268) and releases the schedule (:263-265); the owned scheduler is `shutdown()` (:304) with `removeOnCancelPolicy` (:280), also when called from inside its own tick. `close()` clears watches, releases the schedule, and `shutdownNow()`s the reader pool (:204-215,:465). The pool is 0..4 daemon threads with 5s keep-alive (:438-439), so idle readers die by themselves.
F-A4-1 Low, :243-247 + :272-291: `register` adds the observation to `watches` and only then `ensureScheduledLocked()`; if the scheduler rejects (shut-down external executor) the RuntimeException propagates, but the observation stays in `watches` with no installed gate and nobody ever unregisters it (activeTaskCount leak). Fix: roll back in a catch.
F-A4-2 Low, DefaultRequestHandler:1530: `reconciler.attach(queue)` sits outside the try/detach; if it throws (reconciler closed -> IllegalStateException) the freshly tapped child is never closed. The later `catch ... detach()` covers only reads after attach.
F-A4-3 Info, :203-216: `close()` does not cancel in-flight reads; interrupting a reader makes `onRead` run with the old watch and `failAll` (:381) closes still-attached observers with AUTHORITY_READ_FAILED during shutdown. Installed gates keep working after close, just without detection.
F-A4-4 Info (test strength): `realSchedulerClosesAStrandedObservation...` (:504-535) asserts the `a2a-publication-reconciler` thread is gone before `close()` (good: proves the owned scheduler is shut down by the last unregister, name checked at :527), but its final reader-thread check (:533-534) would also pass without `shutdownNow()` because the 5s keep-alive is shorter than the 10s Awaitility window; no probe covers `close()`'s reader shutdown. Brief's line refs :688-691 are stale (the terminal unregister is :554-556/:608-610).
Discriminating check: probe `terminalcleanup` fails only :349 (count 1 vs 0) - sufficient, but note production would still unregister when the consumer closes the child (:619), so the probe guards promptness, not an unbounded leak. Tests :341 (cancel(false) verified), :360 (pending read cancelled), :375 (closed reconciler) read and confirmed.

## A5. Concurrency/locking
Verdict: No deadlock, lost or duplicated delivery found; two Low findings.
Lock graph I built: (a) distributor: Observation.lock -> child monitor (`offerToQueue` final-event counter EventQueue:1247; full queue -> `close(true)` -> `doClose` -> `onClose` -> `onChildClosed` -> registryLock); (b) MainQueue/child close: child monitor -> registryLock only (`onChildClosed` takes no observation lock, :619-623); (c) registryLock -> TaskWatch monitor (`abandonRead` :261); TaskWatch blocks (:341-348, :363-366, :372-378) take no other lock; (d) `consumed` (obs lock) is called from `dequeueEventItem` outside the child monitor (EventQueue:1284/1294); (e) `fail` takes obs lock, releases it, then `unregister`, then `terminateObservation` (child monitor, then `close(false)`), so it never nests obs lock around a lock that needs it back. No edge returns to obs.lock or registryLock-holders, so the graph is acyclic. Delivery: `ended` (:538,:659) + `watermark` (:538,:682-684) under one lock make every generation delivered at most once, in order; `fail` clears accounting before the error item is queued so a late `consumed` cannot drive counters negative; the error item follows already-delivered items (purge only on overflow). `tickGuarded` catches Throwable (:311), so the fixed-delay schedule cannot be cancelled by a failing tick.
F-A5-1 Low, EventQueue:1323-1327 vs :552-575: `doClose` runs `onClose` *before* `closed = true`. If `installObservation` (volatile write, then `isClosed()`) races a concurrent close in that window, `onClose` saw `observation == null` and `isClosed()` still reads false: nobody calls `onChildClosed`, so the observation (and the scheduler) stays registered for a closed child until a stranded failure fires; on an idle task never. Needs a close concurrent with attach, e.g. main-queue close; very narrow.
F-A5-2 Low, :324-326, :331-336, :385-397: no per-watch / per-observation try/catch. `fail` -> `terminateObservation` -> `close(false)` -> `parent.childClosing` can throw (EventConsumer:118-120 comments that a close can read the task store and throw), which skips the remaining observers of that task in `failAll`/`onRead` and the remaining watches in that tick (poisoned watch is already unregistered at :670, so not repeated forever). Schedule survives; siblings are retried on next tick only if they are still suspect.
Discriminating check: read order of every `synchronized`/monitor entry in PublicationReconciler and ChildQueue (grep + sed above); `tickGuarded` verified by source (no test injects a throwing tick - not examined empirically).
