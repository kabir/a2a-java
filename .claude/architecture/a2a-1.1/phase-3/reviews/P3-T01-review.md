## Findings

### Correctness and extension-point blocker

1. **P1 — `TaskCommitSlot` cannot be used by an atomic store outside the tasks package.** `server-common/src/main/java/org/a2aproject/sdk/server/tasks/TaskCommitSlot.java:27,50,56` makes its constructor, `markCommitted()` and `cancel()` package private, while `AtomicTaskStore.java:31` requires the callback overload. The approved P3-T08 JPA store lives in `org.a2aproject.sdk.extras.taskstore.database.jpa`; it cannot create a token or perform either lifecycle transition. A temporary, outside-package `javac` probe failed with `TaskCommitSlot(String,TaskRevision) is not public ... cannot be accessed from outside package`; `javap -p` also confirmed all three nonpublic members. This blocks the plan's additive `AtomicTaskStore` opt-in across modules and its T01/T03/T08 publication seam (A04/A06). **Smallest correction/test:** expose a documented token lifecycle mechanism usable by external `AtomicTaskStore` implementations, retaining one-way RESERVED → PUBLISHABLE/CANCELLED transitions, and compile a tiny external-package store/probe that reserves, commits and cancels a slot. Do not split the production tasks package across modules.

### Evidence gaps

2. **P2 — post-reservation storage failure is untested.** `InMemoryTaskStore.java:199-239` reserves before `ConcurrentHashMap.compute` returns, then cancels on an unexpected runtime failure; `AtomicTaskStoreContractTest.java:189-205` only makes the reservation callback itself throw. The specific unproven trace is: callback returns after retaining a RESERVED token; the storage operation then fails before a definitive return, possibly after replacement. The plan's T01 acceptance requires a throwing commit never to release a publishable slot, and A06 forbids uncommitted publication. Source inspection shows the intended conservative `TaskMutationOutcomeUnknownException`/cancellation path, so this is an evidence gap rather than a demonstrated rollback or exposure bug. **Smallest test:** inject a controlled `compute` failure after the reservation callback, including an indeterminate after-replacement variant; assert an unknown outcome with preserved cause, a CANCELLED and never PUBLISHABLE token, and no assertion of rollback or safe automatic retry. A small package-local map/fault seam is enough; no JPA or full bus test is needed here.

3. **P3 — legacy interleaving and untorn replacement reads lack a direct regression.** `InMemoryTaskStore.java:134-153,170-211` stores the pair in one immutable entry, uses keyed `compute` for legacy `save`/`delete`, and retains the store-local revision sequence. The current `AtomicTaskStoreContractTest.java:100-144` reads the old pair while planning is blocked; it does not read across repeated replacements or check delete/recreate revision non-reuse. A regression that accidentally separated the task and revision on a later refactor could evade that test. This is relevant to T01 matching-pair/revision acceptance and A05, though the inspected implementation is coherent. **Smallest test:** alternate legacy `save` and atomic mutation on one ID while a reader checks every returned `(task, revision)` pair against known writes; delete and recreate it, then assert the new revision exceeds all previous revisions. Keep a second ID progressing while the first ID's planner is held.

### Documentation precision

4. **P3 — the callback failure Javadoc overstates its exception type.** `AtomicTaskStore.java:24-26` says a callback failure is reported as `TaskMutationNotCommittedException`, but `InMemoryTaskStore.java:205-207` cancels and propagates an `Error` directly. The token and map remain uncommitted on that path; the mismatch matters to an SPI implementer interpreting failure handling. **Smallest correction:** limit the typed-exception promise to runtime callback exceptions and document direct propagation of fatal `Error`s, or otherwise align the contract and implementation. This is not a request to wrap fatal errors as retryable failures.

## Independent assessment

- `ConcurrentHashMap.compute` covers the read, planner guard, revision allocation, reservation and replacement for a task ID, including absent-key creation. `readSnapshot` reads one `StoredTask` entry, so it cannot combine a task from one entry with a revision from another. Legacy `save`/`delete` use the same keyed map operations. The store-local `AtomicLong` avoids revision reuse across deletion/recreation without placing all task IDs under a global critical section; unrelated-ID progress is also exercised by a latch test. A hash-bin collision can cause local contention but is not a global lock.
- The reservation callback runs before leaving the keyed boundary. A successful `compute` return precedes `markCommitted()`. If writer N pauses after replacement, N+1 may commit and become publishable first, but its reservation was observed after N's; T03 can retain that per-task reservation order and hold N+1 until N is publishable or handled as a gap. This is an order-capable local seam, subject to the external-store blocker above and T03's still-unimplemented queue/drain/reconciliation work. No network, fan-out or executor work occurs inside the candidate store callback itself. The no-callback overload intentionally reserves no publication position; T03 must use the callback overload.
- Planner `RuntimeException` and reservation `RuntimeException` are wrapped as definite non-commit with their original causes; an unexpected storage `RuntimeException` becomes outcome-unknown with its cause. A callback `Error` cancels and propagates. `TaskCommitSlot` uses CAS, so cancellation cannot turn an already publishable token back into an uncommitted one, nor can a cancelled token become publishable. The expected planner rejection remains identifiable in the preserved cause chain for downstream typed mapping; later handler/bus mapping must inspect it rather than treating every `TaskStoreException` as an internal server error. That later mapping is outside T01.
- An unchanged plan returns the existing snapshot, empty events, unchanged generation/revision and no slot. `MutationPlan` and `CommittedMutation` copy event lists and reject null required values; `TaskSnapshot` and `TaskRevision` validate required/positive values. A changed batch returns the supplied final Task and original ordered events, including the tested generation-2/generation-3 batch with one generation-3 snapshot. Canonical event/generation validation belongs to T02's pure planner, not to this generic store.
- The original `TaskStore` descriptors and in-memory constructors remain, `get()` returns the stored Task reference, list authorization/projection and `TaskStateProvider` still read stored Tasks, and a legacy-only custom store compiles in the contract test.
