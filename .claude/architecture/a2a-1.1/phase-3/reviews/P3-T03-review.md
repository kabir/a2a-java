### 4. P2 — Cancellation waits for stream termination and returns a later read

**Smallest correction and test.** Complete cancellation from the relevant committed result or a correlated terminal observation carrying its own snapshot. Gate a real completion-vs-cancel race, AUTH_REQUIRED after progress, and a change after terminal delivery before response assembly. Check provenance, typed outcome and resource cleanup.

## Ordering, storage and replication assessment

- Existing-task status and artifact paths use the atomic snapshot, preserve the mutation planner's canonical event and batch-final Task, and hand them through the processor to the in-process publisher. AGENT append events carry the chunk while the snapshot carries accumulated data. There is one final Task snapshot per batch. The publisher compares task ID and store revision to the slot, so earlier event generations need not equal the snapshot's generation. On successful delivery, enqueue of every event precedes the processor's lifecycle and processing callbacks. Consumer-driven closure still depends on the actual event types, terminality, and queue capacity. The new production planners ordinarily return singleton batches, so paired multi-generation lifecycle evidence remains required.
- `InMemoryTaskStore.java:196–251` reserves under the keyed `compute`, keeps the state-transition handle private, and marks its read-only view publishable after replacement. `OrderedTaskPublisher.java:26–44,51–80,86–173` records placeholders under its queue monitor. If N has no attached batch, a ready N+1 returns a pending stage. Attaching N drains N then N+1. An abandoned head can be removed by `discard` or skipped after the store cancels it. Discard racing an active delivery cannot remove its head. The store cannot cancel a publishable handle. Delivery and completion callbacks run outside the store boundary and the publisher monitor. A thrown delivery completes its stage exceptionally and draining proceeds. Synchronous re-entry that merely reserves or submits successor work is possible. A delivery/completion callback synchronously waiting on its own same-task successor deadlocks on the active drainer.
- The processor's publisher is private and the normal single bus thread reserves and attaches each slot before it takes another input. No earlier unresolved slot from another production producer is reachable in that layout. The `join` therefore has no demonstrated predecessor deadlock today on the ordinary delta path. It is non-interruptible and occupies the sole processor plus its ingress permit if a future producer reserves an earlier position whose release depends on that thread. The new inline webhook callback can already introduce a wait through re-entry, for example by waiting for another bus event it queued. Permit release is in the outer `finally` for all returning or throwing paths. It cannot run while the processor is blocked. Avoid carrying a blocking stage wait into an independently produced publication path without proving progress and permit ownership.
- The storage exception mapping distinguishes definite non-commit and unknown outcome and discards a retained placeholder in either case. It suppresses that batch without asserting rollback. There is no input retry, outbox, replay, or lossless guarantee. Unknown storage outcomes can leave a publication gap. Recovery is T14. A delivery-stage failure after a successful commit currently takes the misleading persistence-error path described in finding 5.
- Local nonterminal committed events reach the replication hook as local items. Incoming replicated copies retain the legacy path and flag at the hook, whose replication implementation ignores replicated items. Push skips incoming copies. Terminal committed batches skip the legacy hook as a whole. The stock in-memory store already had no CDI finalization emitter. The legacy JPA store still emits its after-success finalization for states it recognizes, and the existing replication manager synthesizes terminal status followed by a poison pill. The UNSPECIFIED loss in finding 6 is a separate introduced regression. No committed remote provenance, duplicate handling, terminal batch transport, or shared webhook ordering is claimed. Those are T10/T11 work.
- Direct `Message` retains its single-event no-task-mutation path and legacy push/replication eligibility. The `TaskStore` interface and public signatures remain, and the legacy-only path uses the original store calls without emulating an atomic transaction. Per-subscriber version projection remains downstream. The shared core applies the new mutation and error behavior independently of request version, so successful projection alone is insufficient evidence for the compatibility cases above. Full Phase 3 and frozen old-peer revalidation remain outside this review.
