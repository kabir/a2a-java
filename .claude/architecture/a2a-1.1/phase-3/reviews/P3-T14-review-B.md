## B1 — Sink before snapshot
Verdict: sound. I walked tap (DRH:1515) -> `attach` (:1530, installs gate) -> `readAuthoritativeTask` (:1532) -> `complete(G)` (:1537) against the commit/publish order (commit, then `OrderedTaskPublisher`, then `deliverCommittedBatch`, then `distributeToChildren`). Commit <= G is either missed (child not yet tapped) and covered by the snapshot, or arrives and is dropped at `complete` (PR:599) or at `admit` (:538). Commit > G is distributed after the install, so it is held and delivered in order. Items queued before install are taken (:574, EQ:1331). No window where a commit is in neither the snapshot nor the delivered stream.
- Low — EventQueue.java:1226 vs PublicationReconciler.java:574: `observation` is read unsynchronised. A distributor that read `null` before the install and calls `offerToQueue` after `takeQueuedCommittedItems` puts a committed item ungated on the queue. Only a generation <= G can do this, so the result is a duplicate of a snapshot-covered event, never a loss. The "neither lost nor repeated" comment (DRH:1528) slightly overclaims. The duplicate is possible today without a reconciler.
- Low/Info — PublicationGapRecoveryTest:469 calls `complete(5)` after a read that returned 6, a state production cannot produce (it passes `snapshot.generation()`). The test asserts [6,7]; the real G=6 case ([7]) is untested. Probes `discardcovered` (3 failures, 2 errors), `preinstall` ([5,6]) and `snapshotgen` (2 timeouts) did fail on the intended lines (/tmp/t14-probe-*.result).
Discriminating check: the `RacingStore` hook overrides only `readSnapshot` (:799), not `get`, so the hook fires on the post-attach read and not on DRH:1502.

## B5 — Rejection/detach and public API
Verdict: detach is correct. `snapshot == null` and a terminal snapshot both throw inside the try, so `detach()` -> `child.close(true)` -> `onClose` -> `onChildClosed` -> `unregister`, which also releases the scheduler (test :567 asserts 0 observations, not scheduled, no child; probe `detach` fails with expected 0 but was 1). The API additions are additive: `PublicationReconciler` (public `Limits`, `AuthorityHead`, `Attachment`, `attach`, `forTaskStore`, `close`), `Builder.publicationReconciler`, `TaskManager.readAuthoritativeTask`. The failure is an existing `InternalError`; there is no new error code or protocol field.
- Low — DRH:1530: `reconciler.attach(queue)` is outside the `try`. When the reconciler is closed, `register` throws `IllegalStateException` (PR:243) before the install, and the tapped child is never closed. It stays in the main queue's children, so the queue cannot close, and a stream-less child keeps receiving events until its queue fills. Scenario: shutdown closes the reconciler while the handler still serves SubscribeToTask. Fix: move `attach` into the try, or close the child on that failure. Test :383 covers `attach` after `close` but not the handler.
- Low — PR:673-675 / test :114: the message says "retry the subscription or call GetTask". For the stranded-terminal case (the main scenario) a retried SubscribeToTask hits `rejectTerminalSubscription` and fails with `UnsupportedOperationError`. Only GetTask works. The Javadoc guarantee disclaimer is accurate; the message hint is misleading.
