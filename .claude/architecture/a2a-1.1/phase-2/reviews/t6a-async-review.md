## Findings

1. **P2 — Cancelling the result does not stop the default JDK HTTP read.** `JSONRPCTransport.getTaskAsync` stores the future returned by `postAsyncSSE` and calls `cancel(true)` on it at `JSONRPCTransport.java:202-205,211-224`. `JdkA2AHttpClient.asyncRequest` returns `client.sendAsync(...).handle(...)` at `JdkA2AHttpClient.java:385-386`, so the stored future is a dependent stage. Cancelling that stage does not cancel the source `sendAsync` future or its held-open HTTP read. A compiled, network-free Java probe using the same `source.handle(...)` shape printed `returnedCancelled=true, sourceCancelled=false, sourceDone=false`. The controlled-peer cancellation assertion only proves that `TransportCall.result()` fails with `CancellationException`; it does not assert that the peer connection closes or the JDK request stops. This conflicts with the T5 call contract that cancellation detaches the underlying read and leaves a resource leak for delayed or held-open responses. The HTTP future contract must provide an actual cancellation handle or the async adapter must use one that stops the request, with a controlled held-open read regression.

2. **P2 — Async GET can accept a non-success HTTP response as a Task.** The synchronous GET path calls `sendPostRequest`, which rejects every non-2xx status before decoding (`JSONRPCTransport.java:457-464`); async GET instead passes every non-empty callback body to `JSONRPCUtils.decodeTaskResponse` (`JSONRPCTransport.java:211-222`). The JDK SSE helper only handles 401/403 specially and forwards other non-SSE bodies to the message consumer (`JdkA2AHttpClient.java:319-329,334-378`). The Vert.x helper likewise forwards non-SSE bodies, and Android forwards non-2xx error bodies. Thus a 500 response containing a syntactically valid JSON-RPC Task result completes successfully in async GET. The existing controlled peer only returns 200. The async path needs status-aware failure equivalent to the synchronous path, including an HTTP 500 result-body regression. A JSON-RPC error envelope still fails through the named decoder; this finding concerns a non-success status carrying a valid result.

## Final Vert.x handoff re-review — 2026-11-12

**Disposition: accepted for the bounded JSON-RPC async decoded GET slice.** The prior Vert.x P2 cancellation race is closed. `VertxA2AHttpClient.AsyncRequestHandoff` serializes cancellation with request registration and send initiation under one monitor. If cancellation wins before request readiness, the ready callback resets the request and returns without sending. If readiness wins, it stores the reset callback and starts send before cancellation can enter; cancellation then transfers and clears that callback and resets once. If cancellation follows send initiation, it uses the same one-time transfer; repeated `cancel()` calls are idempotent. The `AsyncPostCall.cancel()` guard first cancels the response future, so a completed response is not reset after completion. The deterministic tests exercise cancellation while send setup holds the monitor and cancellation before readiness, asserting one reset in each case and no send in the latter. A Vert.x integration test reads a complete POST, holds its response open, calls cancel twice and observes connection close plus a cancelled response future. This resolves the missing-handle and check-then-send windows identified in the earlier review.
