## Findings

1. **P2 — Public 1.1 GET/LIST still use the evidence-free legacy decoder.** `JSONRPCTransportProvider.capabilities()` advertises only `ORDINARY` for both versions (`JSONRPCTransportProvider.java:17-20`), and the actual transport does the same (`JSONRPCTransport.java:134-137`). `Client.supportsDecodedReads()` selects the companion decoder only if `UNKNOWN_VARIANT_SKIP` is present (`Client.java:621-624`); `Client.getTask`/`listTasks` otherwise invoke legacy reads. The new base peer test obtains the selected wrapper by reflection and calls `selected.listTasksDecoded` directly (`client/base/.../Phase2PublicClientTest.java:70-91`), so it does not test `client.listTasks` or `client.getTask`. Reproduce with the test's Task A/B response containing future timeline generations 8/18, but call public `client.listTasks`: the companion decoder is never selected. This blocks the plan's required public unknown-entry success and feature declaration/selection claim. Once the whole binding is ready, advertise matching implemented features from provider **and** transport, and assert real public GET/LIST plus wrapped SPI envelopes, pagination, known-only returns and malformed-known failure. Keep the 1.0 profile `ORDINARY`.

2. **P2 — A non-2xx SSE response containing a valid JSON-RPC result can be accepted as a successful stream.** `JSONRPCTransport.streamInput` receives only `ServerSentEvent` bodies, with no response status (`JSONRPCTransport.java:351-355`); the versioned listener decodes a valid result and publishes it (`sse/SSEEventListener.java:80-105`). JDK SSE checks only 401/403 specially, then forwards other non-SSE bodies (`JdkA2AHttpClient.java:344-388`); Vert.x does likewise (`VertxA2AHttpClient.java:467-530`), and Android forwards non-2xx error bodies to the message consumer (`AndroidA2AHttpClient.java:278-304`). Reproduce with HTTP **500**, `Content-Type: application/json`, body `{"jsonrpc":"2.0","id":"<echoed request id>","result":{"futureEvent":{}}}` (or a valid Task result). The listener has no way to reject the status and can emit an ignored/known frame followed by normal completion. The unary async GET/SEND paths already reject 500 before decode. Preserve typed JSON-RPC error-envelope handling while making the SSE path reject non-success HTTP status; add a controlled-peer 500-valid-result regression for the raw observation and public completion callback, ideally across all three HTTP backends.

3. **P2 — The response id is checked for shape but not correlated with this stream's request.** `createPostBuilder` generates a fresh UUID through `JSONRPCUtils.toJsonRPCRequest(null, ...)` (`JSONRPCTransport.java:612-620`; `JSONRPCUtils.java:732-740`), while `responseResult` merely calls `getAndValidateId` and discards the value (`JSONRPCUtils.java:431-449`). Every current peer fixture uses a fixed `response-1` id even though the actual request has another UUID, and the 43/43 selector accepts it. The [JSON-RPC 2.0 response rule](https://www.jsonrpc.org/specification#response_object) requires the response id to equal the request id. A peer returning a valid Task or future variant under another request's id is accepted; error envelopes are processed before id correlation as well. Reproduce by recording the outgoing request UUID and returning a different well-formed id with a valid event. Retain the generated id with the call, reject wrong-id result/error envelopes on the selected 1.1 path, and add matching/wrong-id controlled-peer cases. Preserve explicit 1.0 behavior separately.

4. **P2 acceptance evidence gap — required stream outcomes and demand races are not covered at the binding/public seam.** `SSEEventListenerTest` covers known/ignored/malformed and invalid envelopes, but has no `LocalRejection` assertion; the JSON-RPC peer test's sequence omits local `StreamError`, malformed-known public callback, finite demand, buffer overflow, or competing completion/error/cancel. The base public tests cover a normal known/unknown stream and one close/cancellation terminal, not those races (`client/base/.../Phase2PublicClientTest.java:104-171`). Shared `TransportObservation` and earlier shared-client tests establish serialized/exactly-once mechanics, and source shows local rejection mapped to a distinct `TransportFrame` (`sse/SSEEventListener.java:95-98`). They do not prove the complete T6a controlled-peer acceptance bullets: one local rejection frame and public failure, malformed known exactly one public error, finite `request(1)` delivery/buffer behavior, and a held-open terminal/cancel race with no later callback starts. Add those focused tests before complete-binding acceptance.

5. **P2 acceptance evidence gap — two *public* clients with one injected HTTP client are untested.** The held-open test constructs two `JSONRPCTransport` instances with **different** `new JdkA2AHttpClient()` objects (`Phase2PublicClientTest.java:426-431`). The base public close test has only one `Client`. Source supports the intended ownership boundary: transport `close()` cancels its `activeInputObservations` and never closes `httpClient` (`JSONRPCTransport.java:582-586`), and the first transport's close leaves the second stream open in the peer test. The plan asks for closing one of two public clients to leave the other operational, including injected HTTP ownership. Add a two-public-client test using the same injected HTTP client: close one while both have live observations, then prove the other receives another event or completes normally. The current tests support transport-level isolation, not that full claim.
