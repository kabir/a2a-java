## Finding 4 — historical finding, now closed

4. **P2 — Explicit 1.0 JSON accepts snake-case 1.1 artifact provenance and silently discards it.** `spec-grpc/src/main/java/org/a2aproject/sdk/grpc/utils/StreamDecoder.java:327` and `:348` check only `startGeneration` / `endGeneration` (and `role`). A valid Task with an artifact containing `"start_generation":"7"` or `"end_generation":"7"` passes `decodeTaskJson(...,"1.0")`, and the returned artifact has both generations reset to zero. The equivalent camel-case input is rejected. This also affects Task-bearing stream, send and list JSON through the same Task check, and artifact-update JSON through the separate check at line 327. **Violates requirement 8 and T4's frozen legacy JSON strictness:** the old schema has neither field, and the frozen 1.0 protobuf parser rejects each alias with `Cannot find field`. This is a demonstrated version-behavior regression, not a request to implement later output projection. Recognize both spellings when rejecting 1.1-only JSON provenance in explicit 1.0; add Task and artifact-update cases and verify the JSON-RPC paths inherit the rejection. Keep the deliberately separate protobuf-object legacy projection behavior intact.

The three original findings below were closed in the first correction re-review. Finding 4 was found during that re-review and existed in the earlier decoder; it is now also closed by the final re-review.

## Original findings — now closed by the correction re-review

1. **P1 — Streamed Task JSON cannot skip unknown timeline entries.** `spec-grpc/src/main/java/org/a2aproject/sdk/grpc/utils/StreamDecoder.java:128` parses the complete selected payload with strict `JsonFormat` before `decode()` can call `decodeTask()`. A valid Task containing `timeline:[{"generation":"8","futureEntry":{}}]` succeeds through `decodeTaskJson(...,"1.1")`, yielding skipped generation 8, but wrapping that same object in `{"task":...}` and calling `decodeJson(...,"1.1")` returns `Malformed`. `JSONRPCUtils.decodeResponseEvent` delegates to this path (`JSONRPCUtils.java:355`), so HTTP stream snapshots fail on forward-compatible timeline content. **Violates requirement 5 and the shared decode contract:** skip unknown entries while preserving their generation evidence across stream and unary responses. Route Task JSON through timeline normalization before strict parsing and retain its notes; add the same snapshot through direct and JSON-RPC stream regressions.

2. **P1 — Known protobuf JSON aliases are silently classified as unknown, bypassing validation.** `StreamDecoder.java:28` and `:108–117` recognize only camel-case stream member names. The existing protobuf JSON parser accepts original proto field names: a valid `status_update` object parses as `STATUS_UPDATE`, but the new 1.1 decoder returns `Ignored`. Worse, `{"status_update":{}}` also returns `Ignored`, although it is a malformed known update. The same problem applies to `artifact_update` and `message_update`; a camel-case payload beside an aliased known payload can evade the multiple-known-payload check. **Violates requirements 2 and 5:** complete known oneof handling; malformed known content and multiple payloads must remain failures. Recognize protobuf field names and JSON names before unknown classification, including duplicate aliases of one field, and test valid and malformed alias inputs.

3. **P2 — Empty list decoding is stricter than the retained protobuf JSON path.** `StreamDecoder.java:204–206` requires a literal `tasks` array. The generated `ListTasksResponse` with page size 10 and zero tasks prints as `{"pageSize":10}` using ordinary `JsonFormat.printer()`; ordinary protobuf parsing accepts it with zero tasks. The new decoder throws for this representation in both 1.1 and explicit 1.0. `JSONRPCUtils.decodeListTasksResponse` inherits the restriction. **Violates requirement 8's preservation of explicit 1.0 parsing behavior and the list codec consistency requirement.** Treat an omitted repeated field as empty while rejecting a supplied non-array; preserve pagination and an empty per-task notes list. This is demonstrated against the existing protobuf codec, not against a live peer; the current SDK REST server prints defaults and therefore does not trigger this case itself.
