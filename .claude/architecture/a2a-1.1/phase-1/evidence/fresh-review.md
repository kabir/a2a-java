### P1 — keep native 0.3 REST dispatch on its configured default endpoint

`reference/multiversion-rest/src/main/java/org/a2aproject/sdk/server/multiversion/rest/MultiVersionRestRoutes.java:161` treats the captured prefix `v1/` as tenant `v1`. Both ordinary dispatch paths then resolve the registration using that tenant before choosing the 0.3 handler (lines 185–207 and 237–255). However, the unchanged old public 0.3 REST client always uses the historical `/v1` prefix: for example, `compat-0.3/client/transport/rest/src/main/java/org/a2aproject/sdk/compat03/client/transport/rest/RestTransport_v0_3.java:146` and line 148 append `/v1/tasks/...`; send, cancel, subscribe, push configuration and card operations use the same fixed prefix.

Consequently, a default registration enabling 0.3 can reject its public 0.3 client if a distinct 1.x tenant named `v1` is missing or disables 0.3. The inverse setup consults the wrong registration as well. The historical card route was corrected to default/null scope, but ordinary operations still disagree with it.

The user's clarification is binding: **0.3 has no tenants**. The fix must preserve its native configured endpoint and historical path vocabulary. Do not add a 0.3 tenant selector, a tenant parameter in 0.3 wire data, or tenant-qualified 0.3 card guarantees. Currently `server-common/src/main/java/org/a2aproject/sdk/server/version/InterfaceRegistration.java:34` through line 39 permit a non-null tenant with version 0.3 and advertise the resulting descriptor, while the experimental resolver constructs such combinations. Rejecting that new-registration combination is an appropriate conservative boundary; ordinary native 0.3 paths must resolve the default endpoint registration independently of 1.x tenant parsing. Existing legacy entry points must retain demonstrated behavior.

Recommendation: resolve the requested version before applying 1.x tenant interpretation, map only historical native 0.3 REST paths to default endpoint scope, and reject tenant-qualified native 0.3 selection. Keep explicit 1.x tenant `v1` distinct. Verify actual old public 0.3 get/send against divergent default and `v1` registrations, including default enabled/disabled and rejection of fabricated 0.3 tenant requests; keep ordinary 1.x tenant tests and no-resolver historical behavior.

Attempt accounting: this shares the historical-prefix root cause with the REST card finding and must be linked to that ledger row. The retained audit records two failed card implementation/verification cycles and a third focused pass (`rest-final-focused`, ended 15:31:24.727054Z). That pass proved the card case, not all ordinary 0.3 scope. Under the stated material-cycle definition, neither card correction changed ordinary dispatch, so this newly exposed ordinary gap is an initially failing implementation, not three distinct failed ordinary fixes. Do not reset the prior two card failures or relabel a broader failed criterion to evade the safeguard. If the root ledger defined the criterion as all historical REST default scope, preserve that broad criterion as incomplete rather than claiming the focused card pass completed it.
