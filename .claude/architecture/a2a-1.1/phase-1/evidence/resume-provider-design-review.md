## Initial injection-only conclusion (superseded by the atomic-capture addendum below)

Stock gRPC Java 1.81.0 does not expose an API to install an isolated load-balancer factory/registry on NettyChannelBuilder or ManagedChannelImplBuilder. Isolated name resolution is possible; isolated LB construction is not. Consequently there is no fully API-supported construction combining stock Netty managed channels with a fixed SDK LB factory. A transport-factory wrapper can close the known LB tracer slot hole for streams traversing that factory, but it does not by itself establish an enforceable channel boundary: a programmable global LB can return a real subchannel belonging to another channel, and gRPC picks its transport without checking SDK factory ownership.

The most robust design is a pinned gRPC change exposing per-channel LB provider/factory injection, followed by SDK-private resolver and LB instances. This requires an upstream enhancement or maintained gRPC fork/patch (or an explicitly accepted unsupported private-access mechanism). Merely using existing public methods in `io.grpc.internal` is not enough to inject the LB factory. Do not describe stock nameResolverFactory + defaultLoadBalancingPolicy, or the transport-only guard, as complete provider isolation.

## Why transport-only enforcement is incomplete

[`GrpcUtil.java:701`](/tmp/a2a-phase1-run/grpc-source-review/io/grpc/internal/GrpcUtil.java:701) obtains the chosen transport through:

```java
Subchannel subchannel = result.getSubchannel();
transport = ((TransportProvider) subchannel.getInternalSubchannel()).obtainActiveTransport();
```

There is no comparison to the selecting channel, its factory, or its own subchannel set. A globally installed provider may control several channels, retain a helper-created READY Subchannel from an unguarded channel, and pick that object for the SDK channel. Even without inventing an internal TransportProvider, that object already contains one. [`LoadBalancer.java:575`](/tmp/a2a-phase1-run/grpc-source-review/io/grpc/LoadBalancer.java:575) documents helper-created subchannels/wrappers but this path does not enforce same-channel ownership. Such a stream reaches the foreign transport instead of the SDK ClientTransportFactory wrapper. The original SDK tracer executes there before the malicious final LB tracer, reproducing the version mutation hole.

This is a source-derived attack hypothesis, not an executed reproducer. It should be the first adversarial probe before accepting transport-only enforcement. Depending on what API-behavior violations the threat model excludes, the documentation's intended helper ownership may be relevant; relying on that intention does not provide enforced isolation against arbitrary registered callbacks.

A global LB can also create ordinary SDK-factory subchannels to arbitrary addresses with no tracer. A transport wrapper must therefore check selected authority, actual destination address against SDK-owned resolution, and proxy destinations, in addition to metadata/tracers. Resolver isolation alone does not constrain LB-created addresses.

## What an internal transport wrapper can safely accomplish

If a wrapper remains useful as defense in depth or a bounded iteration, make its limits explicit:

- Construct private resolver state via nameResolverFactory; for the smallest dependency surface, use an SDK resolver around ordinary InetAddress resolution. Instantiating `io.grpc.internal.DnsNameResolverProvider` bypasses registry selection but remains an internal dependency and requires auditing DNS service-config/resource-resolver extension behavior.
- Disable retry for an exact SDK-tracer-plus-NOOP shape. Otherwise ManagedChannelImpl appends an internal RetriableStream BufferSizeTracer factory per attempt (ManagedChannelImpl lines 514–520).
- Obtain the exact NOOP identity from `GrpcUtil.getClientStreamTracers(CallOptions.DEFAULT, new Metadata(), 0, false, false)[0]`, not class names or reflection. This relies on the pinned internal implementation; no public stable constant exists.
- At newStream, validate the pin and selected scope; reject a final LB slot unequal to that exact NOOP; enforce all remaining tracer instances are SDK-issued using private identities; clone the tracer array before delegation. A malformed or additional tracer should fail before physical stream construction.
- Snapshot metadata before Netty receives it, then normalize/validate the immutable selected version. Metadata.merge copies the structural entries using System.arraycopy and does not deeply copy serialized bytes or lazy values (Metadata lines 507–515). For robust detached snapshots, serialize with InternalMetadata, clone every name/value byte array, and reconstruct with InternalMetadata.newMetadata. Ordinary retained put/remove metadata references are detached by a fresh merge, but that is a narrower guarantee.
- Return a FailingClientStream on boundary rejection according to ClientTransport.newStream's asynchronous failure contract, keeping tracers' closure balanced. Do not simply throw after allocating a physical stream.
- Delegate scheduler/socket-types/lifecycle/termination correctly. Wrap or reject credential swaps so alternate transport factories cannot silently escape the boundary. Clean up the created factory if later resolver/channel construction fails; ManagedChannelImplBuilder.build constructs the transport factory before resolving/checking the provider (lines 720–729), so that failure path deserves explicit ownership handling.
- Preserve global configurator rejection before and after construction. ConfiguratorRegistry is write-once but may be set after an initial empty read; its getConfigurators call does not freeze it (ConfiguratorRegistry lines 62–79). This is a distinct callback surface, not fixed by resolver isolation.

## Recommended design for a valid enforceable isolation claim

Introduce a gRPC-supported or maintained pinned hook that supplies an exact per-channel LoadBalancerProvider/factory, not a policy-name lookup. Build owned channels with SDK-private name resolution, a known fixed LB implementation, disabled service-config LB replacement, SDK-only interceptors/tracers, and existing opaque-channel rejection. The hook must cover ManagedChannelImpl's service-config parser as well as initial loadBalancerFactory selection; otherwise parsed resolver service config can reintroduce registry-selected policies. Keep the transport guard as extra validation if justified, but do not make it the sole boundary while global programmable LBs can select foreign subchannels.

Residual risks requiring explicit acceptance: internal API/version coupling if using a custom core builder; TLS authority and default-port preservation; owned DNS lifecycle and refresh semantics; factory cleanup on constructor/build failure; retry/hedging semantics if disabled; and source-level verification plus hostile cross-channel-subchannel tests whenever gRPC is upgraded. No stock public combination found satisfies all of these guarantees without the LB injection change.


## Atomic registry capture addendum — revised recommendation

The root proposed a narrower construction that does work against provider replacement in the exact pinned source, without injecting a factory: acquire the default LB registry monitor, inspect the selected provider by exact Java class identity, and build the entire channel while holding that same monitor. With a private direct-address resolver and disabled service-config lookup, the trusted provider is cached forever on the channel. This resolves the foreign-subchannel bypass by preventing the untrusted LB from ever being instantiated for the SDK channel.

### Source verification

- [`LoadBalancerRegistry.java:63`](/tmp/a2a-phase1-run/grpc-source-review/io/grpc/LoadBalancerRegistry.java:63), line 81, and line 125 declare `register`, `deregister`, and `getProvider` as instance `synchronized` methods. Thus `synchronized (registry)` covers all legal provider mutations and the lookup used during channel construction. The registry is final and its default instance is retained; `getDefaultRegistry` cannot be overridden.
- [`AutoConfiguredLoadBalancerFactory.java:43`](/tmp/a2a-phase1-run/grpc-source-review/io/grpc/internal/AutoConfiguredLoadBalancerFactory.java:43) stores both `registry` and `defaultProvider` in final fields. Its constructor selects `registry.getProvider(defaultPolicy)` once. Later `AutoConfiguredLoadBalancer` construction uses this exact `defaultProvider` reference (line 82). Null LB config in acceptResolvedAddresses creates `new PolicySelection(defaultProvider, null)` (lines 94–97). Registry replacement after construction cannot replace this reference.
- [`ManagedChannelImpl.java:569`](/tmp/a2a-phase1-run/grpc-source-review/io/grpc/internal/ManagedChannelImpl.java:569) synchronously creates AutoConfiguredLoadBalancerFactory during builder.build. Building while holding the registry monitor is therefore sufficient; one need not await the asynchronous LB instance creation to capture the trusted provider.
- [`PickFirstLoadBalancerProvider.java:36`](/tmp/a2a-phase1-run/grpc-source-review/io/grpc/internal/PickFirstLoadBalancerProvider.java:36) declares the stock provider final. Checking `provider.getClass() == PickFirstLoadBalancerProvider.class` admits only that exact loaded trusted class. There is no subclass avenue, overrideable comparison, provider getPolicyName callback, or same-name string substitution in this check. Both stock implementations selected by its internal feature flag must be audited: PickFirstLoadBalancer and PickFirstLeafLoadBalancer. Both select helper-created own subchannels with the no-tracer PickResult.withSubchannel overload (PickFirstLoadBalancer line141, PickFirstLeafLoadBalancer line429).
- [`ManagedChannelImpl.java:1635`](/tmp/a2a-phase1-run/grpc-source-review/io/grpc/internal/ManagedChannelImpl.java:1635) when lookUpServiceConfig is false discards resolver config and config selectors and selects EMPTY_SERVICE_CONFIG if defaultServiceConfig is null. The LB therefore receives null policy config (line1729), repeatedly falling back to the final captured defaultProvider. Set disableServiceConfigLookUp, never supply defaultServiceConfig containing a policy, and use a private direct-address resolver which never parses/returns a service config.
- Channel idle/recreation calls the same final factory's newLoadBalancer, so it reuses the captured provider rather than reconsulting the global registry. A later registry mutation therefore cannot introduce a foreign-channel picker or LB tracer on this channel.

### Construction sketch

1. Validate endpoint and resolve it through SDK-owned ordinary DNS or accept literal addresses. Reject unresolved socket addresses. Construct `NettyChannelBuilder.forAddress(SocketAddress)` and apply the selected descriptor authority explicitly where needed for TLS/HTTP authority. This takes the private direct resolver route; the string-host forAddress overload does not.
2. Disable service-config lookup; keep defaultServiceConfig null; disable implicit Census callbacks; reject global configurators with the existing construction checks.
3. Obtain `LoadBalancerRegistry.getDefaultRegistry()` before entering its instance monitor. Inside `synchronized (registry)`, require non-null `registry.getProvider("pick_first")` with exact class identity `PickFirstLoadBalancerProvider.class`, and call builder.build() before leaving the monitor. Direct-address construction defaults to pick_first; do not invoke defaultLoadBalancingPolicy because that method rejects direct addresses.
4. The channel now retains the exact audited stock provider. Do not implement any later registry scans. Existing SDK normalization/final assertions can rely on no untrusted LB callback following them, subject to the audited backend callbacks and global configurator/Census constraints already described.

### Assessment and remaining limits

This is enforceable for the exact pinned 1.81.0 implementation against concurrent register/deregister, including providers registered after successful build. It uses exact class identity rather than class-name matching and an atomic check-and-capture rather than racy scanning. A rejected provider never receives newLoadBalancer/helper/picker access to the SDK channel. Untrusted global provider constructors may already have run during global registry initialization, but ordinary callback APIs do not grant them the SDK channel after this capture.

The technique is not a documented stable public gRPC isolation API. It depends on synchronization implementation details and final default-provider retention, plus the internal stock provider type already pinned to the backend. Label that coupling explicitly. If the user disallows all type-identity gates, even exact class identity, this construction would not meet that policy; do not silently reinterpret such a requirement. Under the stated rejection of class-name checks and racy scans, this construction is materially different and meets the technical requirement.

Direct resolved-address use changes DNS semantics: a selected InetSocketAddress snapshot does not automatically refresh DNS or perform normal host-based multi-address fallback. Preserve host authority for certificates and virtual hosting; define resolution failure, multiple addresses, IPv6, and default ports. A private custom resolver can preserve refresh/fallback while still using atomic trusted-LB capture, but it has more owned lifecycle code. Stock direct resolver is the smallest audited continuation candidate.

A meaningful adversarial test suite should prove: replacement provider before build rejected; registration racing construction cannot be captured after the check; replacement registered after successful construction cannot supply a callback on immediate calls, channel idle/recreation, or reconnection; resolver/DNS service config cannot switch policies; exact stock final class accepted; all protocol calls still emit one selected version with preserved authentication; cancellation/failure and close do not leak the owned channel. No test/build was run by this reviewer.


## Private stock DNS followup review

Reviewed the proposed `forTarget("dns:///" + expectedAuthority).nameResolverFactory(new DnsNameResolverProvider()).disableServiceConfigLookUp()` plus atomic exact-stock pick_first capture. This does preserve stock DNS refresh and multiple-address resolution and bypasses the global NameResolverRegistry. However, the proposal as written retains a public global routing callback through the default ProxyDetector; additionally, disabled service-config application does not stop DNS TXT parsing from calling globally registered LB config parsers. These are separate findings and should not be collapsed into a claim that DNS itself changes the selected LB.

### Confirmed safe resolver/provider properties

`DnsNameResolverProvider` is final and directly constructs DnsNameResolver in both URI overloads (provider source lines 59–94). `nameResolverFactory` recognizes that supplied object as a NameResolverProvider, creates a private NameResolverRegistry, and registers only it (ManagedChannelImplBuilder lines 425–432). The resulting global NameResolverRegistry has no selection role. The stock address resolver field starts as `JdkAddressResolver.INSTANCE` (DnsNameResolver line128), and its resolution uses `InetAddress.getAllByName` (lines 595–601). Returned IPs are turned into ordinary InetSocketAddresses and separate EquivalentAddressGroups (lines212–220), preserving address alternatives.

The ResourceResolverFactory field is private static final and initialized by loading the exact `io.grpc.internal.JndiResourceResolverFactory` class with the DnsNameResolver class loader (lines117–118 and631–673). No gRPC resource-resolver service registry was found. Its protected instance resource-resolver mutation hook is not reachable through the SDK-created final provider path without reflection/package intervention. JNDI ultimately uses standard JVM naming machinery, which is a broader runtime extension boundary; it is not a hidden gRPC tracer/LB installation registry.

### Required correction: disable global proxy callbacks

[`ManagedChannelImpl.java:566`](/tmp/a2a-phase1-run/grpc-source-review/io/grpc/internal/ManagedChannelImpl.java:566) supplies `GrpcUtil.DEFAULT_PROXY_DETECTOR` when the builder has no explicit proxy detector. [`DnsNameResolver.java:251`](/tmp/a2a-phase1-run/grpc-source-review/io/grpc/internal/DnsNameResolver.java:251) calls it before ordinary DNS; a returned proxy address replaces the normal address resolution result (lines291–301).

[`ProxyDetectorImpl.java:149`](/tmp/a2a-phase1-run/grpc-source-review/io/grpc/internal/ProxyDetectorImpl.java:149) obtains `ProxySelector.getDefault()` dynamically, and detectProxy invokes its `select(uri)` method (line222), then asks the global `Authenticator` for credentials (lines232–240). `ProxySelector.setDefault` and `Authenticator.setDefault` are public global registration APIs. Therefore private DNS alone retains programmable routing callbacks. Supply an SDK-owned no-proxy detector, e.g. `builder.proxyDetector(address -> null)`, to eliminate this path. That preserves ordinary direct DNS behavior while deliberately disabling application-configured proxies for this owned contract.

### Service config: discarded selection, but parser callback still happens

The channel's `disableServiceConfigLookUp()` does guarantee the resulting DNS service config and config selector are ignored; ManagedChannelImpl lines1635–1649 selects EMPTY_SERVICE_CONFIG when no SDK default config is supplied. The LB consequently receives null policy config and uses the final captured stock provider. No DNS TXT configuration can replace that provider through this application path.

But [`DnsNameResolver.java:271`](/tmp/a2a-phase1-run/grpc-source-review/io/grpc/internal/DnsNameResolver.java:271) independently consults static `enableTxt`, initialized from system property `io.grpc.internal.DnsNameResolverProvider.enable_service_config` (default false, lines92–93). When enabled, resolution invokes `resolveServiceConfig`, which calls its supplied ServiceConfigParser before publishing the resolution result (line242). That parser is the channel's ScParser. AutoConfiguredLoadBalancerFactory.parseLoadBalancingPolicyConfig then uses its registry (lines185–195), and [`ServiceConfigUtil.java:355`](/tmp/a2a-phase1-run/grpc-source-review/io/grpc/internal/ServiceConfigUtil.java:355) invokes a registered provider's `parseLoadBalancingPolicyConfig` callback. This can occur after the monitor was released, including for a newly registered malicious provider. It is a config-parsing callback only: no channel helper, picker, call options, or call metadata is supplied, and its produced policy is discarded. Thus it does not reintroduce foreign-channel routing or a final LB tracer under the audited code. Nonetheless a strict claim of *no external LB callbacks at all* would be false.

If strict isolation must also exclude these unused config-parser callbacks, wrap the private factory so that it passes the stock DNS provider a copy of NameResolver.Args with an SDK-owned inert ServiceConfigParser. The public Args.toBuilder (NameResolver line540) and Builder.setServiceConfigParser (line631) support that change without reflection. Return a ConfigOrError error from the inert parser (not an arbitrary config object which ManagedChannelImpl would try to cast before the discard branch). Keep disableServiceConfigLookUp as well. This removes dynamic LB registry consultation from DNS config parsing. It does not suppress the optional TXT/JNDI query itself; suppressing it requires a custom resolver or an explicitly accepted pinned-internal mechanism rather than changing global JVM properties for all channels.

### Review disposition

The private stock DNS variant with SDK-owned no-proxy detection and disabled service-config application is a valid way to preserve standard DNS refresh/multiple addresses while preventing provider substitution and the known version-metadata mutation. Add the inert parser wrapper if the accepted contract excludes all programmable gRPC provider callbacks, even callbacks without access to calls. The bare proposal without no-proxy detection is not complete routing isolation. No edits/builds/tests were performed by this reviewer; hostile ProxySelector and TXT-parser probes are recommended alongside the existing provider-race tests before declaring the broader isolation claim verified.
